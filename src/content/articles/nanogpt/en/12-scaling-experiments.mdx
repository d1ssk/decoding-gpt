## What should grow to lower the loss?

In chapter 11, a model with 800,000 parameters was updated 2,000 times and reached a validation loss of about 1.89. To lower the loss further, we could make the model larger, train it longer, or use longer contexts. Each option costs more compute, so the question is where to spend a limited compute budget.

For large language models, the loss has been reported to fall roughly as a power law in parameter count, training tokens, and compute (Kaplan et al. 2020; Hoffmann et al. 2022, Chinchilla). nanoGPT's [`scaling_laws.ipynb`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/scaling_laws.ipynb) reproduces part of the Chinchilla results, and [`transformer_sizing.ipynb`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/transformer_sizing.ipynb) estimates parameter counts, FLOPs, and memory use.

This chapter asks the same questions at a far smaller scale, with 28 training runs that each finish within a few minutes on a CPU.

## Counting parameters and compute

At startup, nanoGPT prints the value of [`get_num_params()`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L150-L160), which by default excludes position embeddings (token embeddings are included because they are shared with `lm_head`). This chapter writes this count as $N$.

Training compute is estimated with the same formula as [`estimate_mfu()`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L289-L303):

```python
N = self.get_num_params()
cfg = self.config
L, H, Q, T = cfg.n_layer, cfg.n_head, cfg.n_embd//cfg.n_head, cfg.block_size
flops_per_token = 6*N + 12*L*H*Q*T
```

The $6N$ per token reflects that each multiply-add with a weight costs 2 FLOPs (a multiplication and an addition) in the forward pass and 4 FLOPs in the backward pass. $12LHQT$ accounts for attention scores and value aggregation. Total training compute multiplies this by the number of training tokens $D$; for small $T$ it is close to $6ND$.

## Experimental setup

Starting from chapter 11's settings (the README's CPU settings), we varied four kinds of conditions. Every run used the same rerun script as chapter 11, which follows the `train.py` procedure, once each with seed 1337.

| Condition               | Settings varied                                                             | Runs |
| ----------------------- | --------------------------------------------------------------------------- | ---: |
| Model size              | `n_embd` ∈ {32, 64, 128, 256} × `n_layer` ∈ {1, 2, 4, 8} (subset)           |   14 |
| Training length         | `max_iters` = `lr_decay_iters` ∈ {250, 500, 1000, 2000, 4000, 8000}         |    6 |
| Context length          | `block_size` ∈ {8, 16, 32, 64, 128, 256}, `batch_size` = 768 / `block_size` |    6 |
| Overfitting and dropout | `n_layer` = 6, `n_embd` = 256, 6,000 updates, `dropout` ∈ {0, 0.2}          |    2 |

The number of components per head was fixed at 32, with `n_head = n_embd / 32`. All other settings, including the learning rate, matched chapter 11.

After training, each model's final loss was computed on 200 windows (each `block_size` characters) drawn from the training and validation splits with a fixed seed. This is steadier than `estimate_loss()`'s 20 batches, but a different choice of windows can shift the value by about 0.02–0.03. For chapter 11's model, this evaluation gives `1.910`, while `train.py` printed `1.886`. **Read differences smaller than 0.03 as within evaluation error.**

### Model size: width matters

Compared at 2,000 updates, the validation loss was determined mainly by `n_embd` (the width):

| `n_embd` | `n_layer` |         $N$ | Validation loss |
| -------: | --------: | ----------: | --------------: |
|       32 |       1–4 | 14.5k–51.5k |       2.43–2.28 |
|       64 |       1–8 |  53.5k–398k |       2.15–2.07 |
|      128 |       1–8 |  205k–1.58M |       1.93–1.90 |
|      256 |       2–8 | 1.59M–6.31M |       1.75–1.77 |

Adding layers at a fixed width changed the loss by 0.08 or less, except for 0.15 at `n_embd = 32`. Comparing two models with almost the same parameter count makes the difference clear:

- `n_layer = 8`, `n_embd = 128` (1.58 million parameters): validation loss `1.905`
- `n_layer = 2`, `n_embd = 256` (1.59 million parameters): validation loss `1.748`

At `n_embd = 256`, going from 2 to 4 to 8 layers gave validation losses of `1.748`, `1.768`, and `1.775`, unchanged within evaluation error, while training time rose from 39 to 214 seconds.

This is an observation limited to these conditions. The learning rate and number of updates stayed tuned for chapter 11's small model, and larger models may be undertrained after 2,000 updates. Studies such as Chinchilla assume that training tokens grow with model size.

Meanwhile, the gap between training and validation loss widened as models grew: `0.027` for `n_embd = 32`, `n_layer = 4`; `0.158` for chapter 11's model; and `0.208` for `n_embd = 256`, `n_layer = 2`. With about one million characters of data, larger models more easily memorize patterns specific to the training data.

### Training length: every doubling of updates lowers the loss

Keeping chapter 11's model size, we varied the number of updates. Each learning-rate schedule decays fully by its own `max_iters`.

| `max_iters` | Tokens processed | Passes over training data | Training | Validation |   Gap |
| ----------: | ---------------: | ------------------------: | -------: | ---------: | ----: |
|         250 |             193k |                       0.2 |    2.400 |      2.422 | 0.022 |
|         500 |             385k |                       0.4 |    2.270 |      2.308 | 0.038 |
|       1,000 |             769k |                       0.8 |    2.050 |      2.130 | 0.080 |
|       2,000 |            1.54M |                       1.5 |    1.752 |      1.910 | 0.158 |
|       4,000 |            3.07M |                       3.1 |    1.538 |      1.732 | 0.194 |
|       8,000 |            6.14M |                       6.1 |    1.399 |      1.615 | 0.216 |

Each doubling of updates lowered the validation loss by 0.11–0.22. Going from 2,000 to 8,000 updates lowered it from `1.910` to `1.615` with 3.2 × 10¹³ FLOPs. Making the model about 8 times larger (`n_embd = 256`, `n_layer = 8`) for the same 2,000 updates used about twice the compute, 6.1 × 10¹³ FLOPs, and reached only `1.775`. In experiments at this scale, training the same model longer gave more improvement per unit of compute than making the model larger.

Repeated passes over the training data widen the gap between training and validation loss, however. In the 8,000-update run, `estimate_loss()`'s validation loss rose from `1.577` at update 7,000 to `1.625` at update 8,000, a sign that overfitting was beginning.

### Context length: a trade-off with the number of sequences

We fixed the tokens per update at 768 and varied `block_size` ($T$) together with the batch size ($768/T$). Each line in the diagram is the validation loss at each position $t$ of the input sequence, averaged over position ranges 0, 1, 2–3, 4–7, and so on. A prediction at position $t$ can use only $t + 1$ characters of context, so every model has its largest loss at position 0 (2.47–2.75), and the loss falls as context grows.

Averaged over the whole sequence, the validation loss was lowest at $T = 32$ (`1.864`), with `2.006` at $T = 8$ and `2.186` at $T = 256$. Even near the start, at position 7, the models with $T = 128$ and $T = 256$ have larger losses (`2.05`, `2.08`) than those with $T = 16$ and $T = 32$ (`1.85`, `1.81`).

In this experiment, a larger $T$ means fewer independent text sequences per update (only 3 at $T = 256$). The gradient noise from so few sequences may have dominated before the models could learn to use long contexts, and this experiment cannot separate the two effects. The source repository's `train_shakespeare_char.py` pairs `block_size = 256` with `batch_size = 64`, using 16,384 tokens per update. Testing the effect of long contexts requires keeping the number of sequences per batch while increasing the training budget.

### Overfitting and dropout

A model with `n_layer = 6` and `n_embd = 256` (4.73 million parameters) was trained for 6,000 updates (about 4.6 passes over the data), comparing `dropout` 0 and 0.2. `estimate_loss()` used `eval_iters = 100`, more batches than in the other experiments.

- `dropout = 0`: the validation loss at update 6,000 was `1.550` and kept falling until the end. The gap to the training loss widened from `0.122` at update 1,000 to `0.208` at update 6,000.
- `dropout = 0.2`: both training and validation losses fell more slowly, and the validation loss at update 6,000 was `1.647`. The gap was `0.200` at update 6,000.

Within this range, dropout barely narrowed the gap between training and validation loss, and the validation loss ended higher. Dropout slows learning in exchange for limiting overfitting, so its benefit likely appears only when training continues until the validation loss starts to rise. The source configuration file uses `dropout = 0.2` for a larger model trained for 5,000 updates.

## Reading the results and their limits

These results come from small conditions: Tiny Shakespeare (about one million training characters), a character vocabulary, at most 6.31 million parameters, and a few minutes of CPU time.

- Each condition was trained once; variation across seeds was not measured.
- The learning rate and other settings stayed tuned for chapter 11's model rather than being adjusted per condition.
- The evaluation has an error of about 0.02–0.03.

Even so, the experiments show that model width, training length, and the amount of data interact, and that the way compute is spent changes the outcome substantially. Large-scale studies run such experiments systematically over wide ranges to find the compute-optimal model size and number of training tokens.

## Verify in code

Parameter counts and compute estimates can be computed without training. Run this from the nanoGPT directory:

```python
from model import GPT, GPTConfig

for n_layer, n_embd in [(4, 128), (2, 256), (8, 256)]:
    n_head = n_embd // 32
    model = GPT(GPTConfig(n_layer=n_layer, n_head=n_head, n_embd=n_embd,
                          block_size=64, vocab_size=65, bias=False, dropout=0.0))
    N = model.get_num_params()
    # The per-token count used inside GPT.estimate_mfu()
    L, H, Q, T = n_layer, n_head, n_embd // n_head, 64
    flops_per_token = 6 * N + 12 * L * H * Q * T
    tokens = 12 * 64 * 2001
    print(n_layer, n_embd, N, flops_per_token, f"{flops_per_token * tokens:.2e}")
```

After each model's parameter count, the generation environment printed:

```text
4 128 795904 5168640 7.94e+12
2 256 1590784 9937920 1.53e+13
8 256 6312448 39447552 6.06e+13
```

Each line gives the number of layers, the embedding dimension, $N$, FLOPs per token, and FLOPs over all 2,001 updates. To train one of these models, change `--n_layer`, `--n_head`, `--n_embd`, `--max_iters`, `--lr_decay_iters`, and similar options in chapter 11's command:

```bash
python train.py config/train_shakespeare_char.py --device=cpu --compile=False \
  --eval_iters=20 --log_interval=1 --block_size=64 --batch_size=12 \
  --n_layer=2 --n_head=8 --n_embd=256 --max_iters=2000 --lr_decay_iters=2000 \
  --dropout=0.0
```
