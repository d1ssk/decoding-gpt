nanoGPT is a compact codebase for training and generating with GPT-2-style language models. At its center are roughly 300 lines in `model.py`, which define the model, and roughly 300 lines in `train.py`, which run training. Data preparation, configuration, generation, and benchmarking code surround those two files.

The repository is small, but it is not a line-by-line teaching implementation. GPU execution, mixed precision, distributed training, checkpoints, and loading GPT-2 weights all live in the same code. Reading it from the first line to the last can therefore hide the main idea. It is easier to begin with the path of **one batch of tokens across files and through tensor transformations**.

nanoGPT can be organized into four parts:

1. Data preparation that turns text into a token stream
2. The GPT model that turns tokens into next-token predictions
3. The training loop that turns loss into parameter updates
4. Sampling that turns trained weights into generated text

All upstream references are pinned to [`karpathy/nanoGPT`](https://github.com/karpathy/nanoGPT/tree/3adf61e154c3fe3fca428ad6bc3818b27a3b8291) at commit `3adf61e154c3fe3fca428ad6bc3818b27a3b8291`. Source links and line numbers on this page refer to that commit.

## What nanoGPT covers

nanoGPT is centered on **next-token prediction** with a decoder-only Transformer. Given a token sequence, the model assigns a score to every possible next token at every position. Repeating that computation over a large text corpus gives us pretraining. Continuing from existing weights with a lower learning rate gives us fine-tuning. Feeding each predicted token back into a trained model gives us generation.

```text
pretraining   : random weights + token data → trained weights
fine-tuning   : pretrained weights + new token data → adapted weights
generation    : trained weights + prompt → one token → append → repeat
```

nanoGPT alone is not an entire ChatGPT-like system. Conversation formats, instruction tuning, preference optimization, tool use, serving, and a chat UI are outside its core scope. This series first uses nanoGPT to understand the language-modeling core, then moves to nanochat for a wider stack.

### 1. Turn data into token IDs

The model never receives strings directly. A `prepare.py` script tokenizes text and converts it into a sequence of integers.

The character-level [`data/shakespeare_char/prepare.py`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/data/shakespeare_char/prepare.py#L19-L61) gathers the characters in the corpus, uses `stoi` to map characters to IDs, and uses `itos` for the reverse direction. Datasets that use the same BPE as GPT-2 rely on `tiktoken` for that role.

Data preparation produces three central artifacts:

- `train.bin`: the token stream used for parameter updates
- `val.bin`: a separate token stream used to estimate loss
- `meta.pkl`: vocabulary size and encode/decode metadata for character data

The binary files contain one long concatenated token stream, not a table of documents. Training constructs context windows by taking slices from that stream.

### 2. Create inputs and targets one token apart

[`get_batch()` in `train.py`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/train.py#L114-L131) selects random starting positions. It takes `block_size` tokens for input `x` and the same window shifted forward by one token for target `y`.

```text
token stream : G  P  T  predicts  the  next  token
input x      : G  P  T  predicts  the  next
target y     : P  T  predicts  the  next  token
```

If batch size is $B$ and context length is $T$, both `x` and `y` have shape $B \times T$. One forward pass therefore evaluates $B \times T$ next-token predictions at once.

### 3. Let GPT compute logits

`x` enters [`GPT.forward()`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L170-L193). The model adds token and position embeddings, passes the result through multiple Transformer blocks, and uses a language-model head to produce one score for every vocabulary token.

```python
logits, loss = model(X, Y)
```

The logits have shape $B \times T \times V$, where $V$ is vocabulary size. `logits[b, t, v]` is the unnormalized score for token `v` being next at position `t` in batch item `b`.

### 4. Update parameters from the loss

When targets are provided, `GPT.forward()` also computes cross entropy over all positions. The training loop differentiates this scalar loss and lets AdamW update the parameters.

```python
optimizer.zero_grad(set_to_none=True)
loss.backward()
optimizer.step()
```

The real `train.py` adds gradient accumulation, a `GradScaler` for mixed precision, gradient clipping, a learning-rate schedule, and DDP gradient synchronization around this core. Most of that complexity exists to run larger training jobs efficiently and reliably; it does not change the meaning of the model itself.

### 5. Save checkpoints and generate

At regular intervals, training estimates train and validation loss and saves model parameters, optimizer state, the iteration number, and configuration in a checkpoint. `sample.py` restores a checkpoint and calls `model.generate()`. The loop that extends the sequence one token at a time lives inside `generate()`.

Generation has no target `y`. It scales the logits from the final position by temperature, optionally removes everything outside the top-k candidates, applies softmax, and samples one next token. That token is appended to the input and the process repeats.

## Inside `model.py`

`model.py` defines `LayerNorm`, `CausalSelfAttention`, `MLP`, `Block`, and `GPT`, moving from small modules to the complete model. At runtime they are nested like this:

```text
GPT
├── token embedding (wte)         [V, C]
├── position embedding (wpe)      [T, C]
├── Block × n_layer
│   ├── LayerNorm
│   ├── CausalSelfAttention
│   │   ├── c_attn                C → 3C (Q, K, V)
│   │   └── c_proj                C → C
│   ├── LayerNorm
│   └── MLP                       C → 4C → C
├── final LayerNorm
└── language-model head           C → V
```

Here $C$ is the embedding dimension. The central shapes move through the model as follows:

| Stage               | Shape                            | Meaning                                         |
| ------------------- | -------------------------------- | ----------------------------------------------- |
| Token IDs           | $B \times T$                     | Indices into the vocabulary                     |
| Token embeddings    | $B \times T \times C$            | Learned vectors for tokens                      |
| Position embeddings | $T \times C$                     | Learned vectors for positions in the sequence   |
| Query / key / value | $B \times H \times T \times C/H$ | Per-head representations                        |
| Attention weights   | $B \times H \times T \times T$   | Weights from each position to earlier positions |
| Residual stream     | $B \times T \times C$            | Hidden states flowing between blocks            |
| Logits              | $B \times T \times V$            | Scores for next-token candidates                |

### Causal self-attention

[`CausalSelfAttention`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L29-L76) projects its input into queries, keys, and values, then separates them into multiple heads. One head approximately computes:

$$
A = \operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_{\text{head}}}} + M\right),
\qquad Y = AV
$$

$M$ is a causal mask. It assigns $-\infty$ to future positions, making their weights zero after softmax. A prediction at position $t$ can therefore use positions $0$ through $t$, but it cannot see the future token that serves as its target.

When PyTorch supports it, nanoGPT uses the fused `scaled_dot_product_attention` implementation. Otherwise it explicitly computes the mask, softmax, and value product in Python. The meaning is the same, although the explicit path is easier to inspect.

### The MLP and residual stream

Attention mixes information across token positions. The [`MLP`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L78-L92) instead transforms the channels at each position. It expands the dimension from $C$ to $4C$, applies GELU, then projects back to $C$.

[`Block`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L94-L106) adds the outputs of attention and the MLP back to the original `x`. These residual connections keep the shape at $B \times T \times C$ through every block. Later chapters will follow how the values inside that same-shaped container change from layer to layer.

### Returning to logits

After all blocks, a final LayerNorm is followed by `lm_head`, which converts each $C$-dimensional hidden state into $V$ logits. The token embedding and `lm_head` share their weights. The same table that turns token IDs into input vectors is reused to score tokens at the output.

## Reading `train.py` by responsibility

`train.py` looks long, but it becomes manageable when divided into six sections:

1. **Default configuration** — dataset, model size, optimizer, evaluation cadence, and device.
2. **Runtime setup** — single-process or DDP execution, random seeds, device, dtype, and autocast.
3. **Data loading** — open binary data through `np.memmap` and build `X, Y` in `get_batch()`.
4. **Model setup** — start from scratch, resume a checkpoint, or load pretrained GPT-2, then configure the optimizer.
5. **Evaluation and scheduling** — estimate train/validation loss, compute the learning rate, and decide when to checkpoint.
6. **Training loop** — repeat forward, backward, gradient processing, optimizer steps, and logging.

There are three entry points for model initialization:

| `init_from` | Starting state                             | Use                                  |
| ----------- | ------------------------------------------ | ------------------------------------ |
| `scratch`   | Randomly initialized weights               | Start pretraining from the beginning |
| `resume`    | Model and optimizer from `out_dir/ckpt.pt` | Continue an interrupted run          |
| `gpt2*`     | GPT-2 weights loaded through Hugging Face  | Begin evaluation or fine-tuning      |

These paths start with different weights but eventually join the same `GPT` instance and training loop.

## Configuration defines the experiment

nanoGPT starts from defaults in `train.py` and overrides architecture and training settings through `config/*.py` and `--key=value`. [`configurator.py`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/configurator.py#L20-L47) is small, but it is important for experiment reproducibility.

The upstream defaults and the character-level Shakespeare configuration operate at very different scales:

| Setting             | `train.py` default | Shakespeare character config |
| ------------------- | -----------------: | ---------------------------: |
| Context length      |               1024 |                          256 |
| Transformer blocks  |                 12 |                            6 |
| Attention heads     |                 12 |                            6 |
| Embedding dimension |                768 |                          384 |
| Dataset             |        OpenWebText |             Tiny Shakespeare |

Model size is not the only relevant condition. Batch size, learning rate, iteration count, dropout, evaluation count, and device all change the result and runtime. Running “the same code” is not enough to reproduce an experiment; the configuration and source commit must be recorded too.

## Where training and generation diverge

Training and generation share the same model from token IDs through hidden states and logits. They differ in how those logits are used.

|                    | Training                                | Generation                               |
| ------------------ | --------------------------------------- | ---------------------------------------- |
| Model input        | Token IDs `X` and targets `Y`           | A prompt and all tokens generated so far |
| Logits needed      | Every one of the $B \times T$ positions | Only the final position                  |
| Use of logits      | Compute cross entropy                   | Apply softmax and select a token         |
| Parameters         | Updated through gradients               | Held fixed                               |
| Unit of repetition | One batch                               | One generated token                      |

This makes it clear that `train.py` and `sample.py` do not use separate models. They call the same `GPT.forward()` for different purposes.

## A recommended source-reading order

For a first pass, follow values in this order instead of reading every file from the top:

1. Open [`data/shakespeare_char/prepare.py`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/data/shakespeare_char/prepare.py) and connect text to token IDs.
2. Inspect [`train.py:get_batch()`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/train.py#L114-L131) and verify that `X` and `Y` differ by one token.
3. Read [`GPT.forward()`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L170-L193) once from embeddings to logits.
4. Descend into [`Block`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L94-L106) and [`CausalSelfAttention`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L29-L76), tracking intermediate shapes.
5. Return to the [`train.py` training loop](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/train.py#L249-L333) and follow the loss through the update.
6. Finish with [`GPT.generate()`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/model.py#L305-L330) and [`sample.py`](https://github.com/karpathy/nanoGPT/blob/3adf61e154c3fe3fca428ad6bc3818b27a3b8291/sample.py), where each output token becomes the next input.

This route completes one pass through the language-modeling computation before introducing distributed training and performance details.

## How this series proceeds

The remaining chapters revisit the same end-to-end path in four phases.

### Phase 1 — Build the data

Chapters 1–2 turn text into token IDs and build context windows and targets from a long token stream. The central values are `stoi` / `itos`, the token stream, `X [B,T]`, and `Y [B,T]`.

### Phase 2 — Decompose the forward pass

Chapters 3–8 split `GPT.forward()` into embeddings, positions, self-attention, multiple heads, the MLP, the residual stream, logits, and loss. At each stage we will inspect not only tensor shapes but also value ranges and the meaning of each axis.

### Phase 3 — Watch the model learn

Chapters 9–11 follow gradients from the loss, inspect how the optimizer updates parameters, and interpret train and validation loss. The phase ends by training a small GPT and comparing its output before and after training.

### Phase 4 — Move to scale and a wider system

Chapter 12 experiments with tradeoffs among parameter count, context length, batch size, and compute. Chapter 13 starts from the pretraining core learned in nanoGPT and examines the additional data, evaluation, inference, and chat-oriented stages introduced by nanochat.

## Data and model computation

nanoGPT becomes easier to navigate when remembered as two connected paths:

```text
data path:
text → prepare.py → train.bin → get_batch → X / Y

model path:
X → GPT.forward → logits → loss → backward → optimizer → checkpoint
                                            checkpoint → generate → text
```

As later chapters zoom into individual equations and modules, we can identify where each one fits in the overall computation. The goal is not to memorize filenames. It is to explain **where a token ID becomes a vector, where it receives context, where it becomes next-token scores, and where those scores lead to parameter updates**.
